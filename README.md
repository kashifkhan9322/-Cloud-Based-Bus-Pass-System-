# Wayfare — Cloud-Based Bus Pass System

A responsive, cloud-ready bus pass booking web application built with Node.js (built-in modules only), HTML, CSS, and vanilla JavaScript. It demonstrates digital ticket booking, server-side fare calculation, ticket retrieval, input validation, basic rate limiting, security headers, automated tests, containerization, and a deployment path for AWS.

> **Academic project note:** This is a functional demo, not a production ticketing/payment platform. It does not collect payments, authenticate users, or integrate with a real transit operator. For production, replace local JSON storage with a transactional database and add identity, payment, monitoring, backups, and operational controls.

## Features

- Responsive, polished booking UI with route cards and fare summary.
- Four sample routes and three pass types: single ride, day pass, weekly pass.
- Server-authoritative price calculation; client-supplied prices are ignored.
- Unique booking ID and ticket code for each confirmed booking.
- Ticket lookup by ticket code.
- Validation for email, date, route, pass type, and quantity (1–5).
- Persistent local demo storage using atomic file replacement.
- API health endpoint, security headers, request body limit, and simple per-IP rate limit.
- Automated integration tests using Node's built-in test runner.
- Dockerfile and Docker Compose setup with a persistent volume.
- AWS deployment architecture and production-hardening checklist below.

## Requirements

- Node.js 20 or later (Node.js 22 recommended).
- Or Docker Desktop / Docker Engine with Compose.

No npm dependencies are required.

## Run locally

### Windows PowerShell

```powershell
# Open PowerShell in the extracted project folder
node --version
npm test
npm start
```

Open http://localhost:3000 in your browser.

### macOS / Linux

```bash
node --version
npm test
npm start
```

Open http://localhost:3000.

Stop the server with `Ctrl+C`. Bookings are stored in `data/bookings.json` by default. Do not commit real personal information to source control.

## Run with Docker

```bash
docker compose up --build
```

Open http://localhost:3000. The Compose volume `wayfare-data` persists bookings across container restarts.

Stop:

```bash
docker compose down
```

## Tests

```bash
npm test
npm run check
```

The integration tests start a temporary server and isolated temporary data directory. They verify health, route data, fare integrity, weekly-pass pricing, invalid inputs, ticket lookup, unknown ticket handling, and security headers.

## API reference

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/api/health` | Service health check |
| `GET` | `/api/routes` | Sample routes and pass types |
| `POST` | `/api/bookings` | Create a booking |
| `GET` | `/api/bookings/:ticketCode` | Retrieve a booking by ticket code |

### Example booking request

```json
{
  "passengerName": "Amaan Khan",
  "email": "amaan@example.com",
  "routeId": "R101",
  "passType": "day",
  "travelDate": "2026-10-10",
  "quantity": 1
}
```

Example response fields:

```json
{
  "booking": {
    "ticketCode": "BP-A1B2C3D4E5F60718",
    "routeName": "Central Station → Tech Park",
    "passLabel": "Day pass",
    "unitPrice": 75,
    "totalPrice": 75,
    "status": "CONFIRMED"
  }
}
```

The ticket code above is illustrative. Actual codes are generated by the running application.

### Sample pricing logic

The server stores each route's base fare and applies the pass multiplier:

| Pass | Multiplier | Example on ₹25 route |
|---|---:|---:|
| Single ride | 1× | ₹25 |
| Day pass | 3× | ₹75 |
| Weekly pass | 14× | ₹350 |

These multipliers are demonstration assumptions, not official transit fares. Edit `ROUTES` and `PASS_TYPES` in `server.js` for your project requirements. Fare calculation must remain server-side.

## Important design decisions and limitations

1. **Fare integrity:** The browser displays an estimate, but the server independently derives the total from trusted route/pass configuration.
2. **Ticket retrieval:** A cryptographically random ticket code maps to a persisted booking. Keep the code private; production should add owner verification or authenticated access.
3. **Storage:** JSON storage is suitable only for a single-process demo. It is not safe for concurrent multi-instance writes and is not a substitute for a transactional database.
4. **Scaling:** The Docker image is stateless except for the mounted demo data volume. For real horizontal scaling, use managed database storage and shared object storage; do not mount one JSON file across multiple app replicas.
5. **Payment:** No payment is processed and a confirmed booking here means demo reservation only.
6. **Privacy:** This demo stores passenger name and email locally. Use synthetic data for screenshots and submissions.
